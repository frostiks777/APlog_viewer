# ADR 0001 — Модель чтения логов, API и границы MVP

Дата: 2026-11-13. Статус: принято.

## Контекст

Логи лежат на SMB-шарах (`\\host\c$\...`), размеры — от 80 КБ до 6–14 МБ на файл, суточная
ротация через `file.log -> file.0.log` + новый `file.log`, редко — гигабайты. Пользователь
один, смотрит браузером с той же машины. Референс — UVviewsoft LogViewer.

Проведён внешний архитектурный аудит плана (`APlog_Viewer_review.md`). Ниже — решения,
которые меняют план, и отклонённые рекомендации с причиной.

## Решение 1. Чтение: позиционные окна, без mmap

Читаем `FileHandle.read(buffer, 0, N, position)` блоками 64 КБ; в памяти только окно и
распарсенные строки. Скроллбар привязан к байтам, не к строкам. Файл не открывается целиком
никогда.

**Отклонено:** `mmap` (в стиле Lister). По SMB отображение файла в память ломается при
обрыве шары и не даёт контроля над окном; позиционное чтение даёт тот же профиль памяти
при предсказуемом поведении.

**Следствие:** точный номер строки нельзя узнать без прохода от начала файла. Это
компенсируется разреженным индексом (шаг 1024 строки) и признаком «номер неизвестен»
вне проиндексированного префикса.

## Решение 2. Идентичность файла: `sourceId` + `identity` + `generation`

- `sourceId` — запись профиля (путь + подпись), стабильна между сессиями.
- `identity` — `dev:ino` из `fs.stat({bigint:true})`, то есть том + NTFS File ID.
- `generation` — эпоха содержимого: инкремент при ротации (смена `identity`) и при усечении
  (размер стал меньше).

Индекс строк привязан к `sourceId + generation`, поэтому ночное переименование
`portal.log -> portal.0.log` сохраняет индекс (тот же `identity`), а новый `portal.log`
получает новую генерацию.

**Отклонено как доказательство:** ключ `path+size+mtime` и отпечаток первых/последних 4 КБ.
Изменение середины файла их не меняет. Допустимо только как эвристика с явной пометкой
`trust: weak` и перестройкой индекса при любом сомнении.

**Ограничение, которое принимаем:** «только дописывание до ротации». Если писатель
перезаписывает файл на месте, viewer не обязан замечать изменение середины; такой сценарий
фиксируется как неподдерживаемый.

## Решение 3. Tail: polling по размеру и идентичности, без удержания хендла

Опрос раз в 1.5 с: `stat` → сравнение `identity` и размера → чтение от курсора. Tail
открывает и закрывает файл на каждый опрос: иначе ротация через `rename` на шаре падает
у писателя с `EPERM` (проверено).

События: `ok` (дописывание), `rotated` (сменился `identity`), `truncated` (размер меньше
предыдущего). При `rotated`/`truncated` клиент перечитывает файл с начала — курсор прошлого
поколения к новому неприменим.

**Отклонено:** `mtime` как единственный сигнал (Windows не гарантирует своевременное
обновление при открытом писателе) и `fs.watch` на SMB (ненадёжен, документировано в Node).

## Решение 4. Кодировки и границы строк — часть ядра

Разделение на строки кодировко-зависимое: LF для однобайтовых, `0A 00`/`00 0A` для
UTF-16LE/BE. BOM снимается с текста первой строки. CRLF и LF поддерживаются, последняя
строка без перевода считается строкой. Всё это покрыто `scripts/check-encodings.mjs`.

**Отклонено:** независимое декодирование произвольных чанков. Страницы режутся только по
границам строк, поэтому многобайтовый символ не разрывается.

**Ограничение:** автоопределение — гипотеза, а не гарантия (ASCII валиден в нескольких
кодировках). Выбранная кодировка показывается в UI и переопределяется вручную на вкладку.

## Решение 5. Regex: построчный, JS-диалект, в worker с бюджетом

Семантика MVP: регулярное выражение применяется к одной строке; многострочные совпадения
(stack trace) — отдельная задача. Один и тот же matcher используется для подсветки, правил
и поиска.

**Отклонено:** RE2. Даёт защиту от REDOS, но теряет look-around и backreferences и требует
нативной сборки под Windows. Риск катастрофического бэктрекинга закрывается иначе: поиск
идёт в `worker_threads` с бюджетом времени и отменой, а правило, превысившее бюджет,
отключается с предупреждением.

**Отклонено в MVP:** фильтрация как отдельный индекс результатов. Скрытие строк работает в
пределах загруженного буфера и помечается «неполный просмотр»; экспорт фиксирует
`generation` и `endByte`.

## Решение 6. Локальный API: Host/Origin, без токена

Сервер слушает `127.0.0.1`. На каждый запрос проверяются `Host` и (если есть) `Origin` по
allowlist; CORS не разрешён. Этого достаточно против чужой веб-страницы, которая пытается
достучаться до localhost (DNS rebinding / CSRF).

**Отклонено:** обязательный токен/сессия в MVP. Токен не защищает от процесса того же
пользователя (он прочитает профиль), а браузерный вектор закрывается проверкой Origin.
Токен появится вместе с сетевым доступом (`auth: token`), тогда же — ограничение списка
разрешённых корней.

## Решение 7. Границы MVP

В MVP **не входят**: агрегаты `/stats` без парсера событий, многострочный regex, точная
геометрия OS-окна, отдельный helper-процесс для SMB I/O, SSE-канал для tail.

- Агрегаты требуют парсера: конкретный кандидат — NDJSON-сайдкар `StdioProcessor.log.json`.
  Без него «средний уровень по файлу» — выдумка.
- Геометрию окна браузера страница не контролирует (CSSOM); сохраняем панели, шрифт, byte
  anchor.
- Отдельный процесс для SMB — страховка от зависшего I/O; при одном пользователе и лимите
  одновременных чтений (2) достаточно ограничить конкурентность, а решение пересмотреть
  после теста с обрывом шары.
- Tail на polling идемпотентен по byte offset и не требует replay; SSE добавит
  `resync_required`, который сейчас не нужен.

## Решение 8. Профиль и кэш раздельно

`profile.json` (настройки) и `cache/` (восстанавливаемые индексы) — разные каталоги.
Профиль пишется через tmp + rename с повтором на `EPERM`/`EBUSY` (антивирус держит хендл),
предыдущая версия остаётся как `.bak`, битый файл восстанавливается из бэкапа. GC кэша —
по `lastUsed`, а не по дате создания.
