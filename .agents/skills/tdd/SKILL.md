# TDD (Test-Driven Development, адаптация)

Скилл «сначала тест, потом код». Применяется для нетривиальной логики и UI с поведением.

## Когда применять

- Новая функция / route handler (`POST /api/bookings`, `formatDate(...)`).
- Новый кастомный хук (`useSlots`, `useBookingForm`, `useAvailability`).
- Новый компонент с пользовательским взаимодействием (форма, диалог, кнопка с эффектом).
- Любая логика со «входящими → преобразование → исходящие», которую можно воспроизвести.

## Когда НЕ применять

- Type-only правки (поменяли `interface` без изменения поведения).
- Рефакторинг без изменения сигнатур (вынесли хелпер, переименовали переменную).
- Чисто документные/конфигурационные изменения (`AGENTS.md`, `tailwind.config.js`).
- Однострочные правки в существующих тестах.

## Алгоритм для бэкенда (route / утилита)

```markdown
1. ✅ Базовая проверка: команда тестов проекта — все зелёные.
2. 🟥 Создать тест рядом с кодом в принятом в проекте стиле:
   - Описать **ожидаемое** поведение (входы, ключевые ветки, ошибки).
   - Прогнать тест → он должен быть красным (Red).
3. 🟩 Реализовать **минимум** кода, чтобы тест стал зелёным (Green).
4. 🔁 Рефакторинг, пока тест всё ещё зелёный (Refactor).
5. ✅ Финальная проверка: чек-чейн из `.agents/shared/checks.md`.
```

**Тест-кейсы, которые обязательно покрыть для API-роута:**

- Happy path (валидный вход → ожидаемый статус + тело).
- Validation error (битый вход → клиентская ошибка).
- Resource-not-found или conflict (повторная операция → `404`/`409`).

**Пример:** добавление нового `POST`-роута:

1. Тест: валидный запрос → ожидаем `201` и тело с идентификатором. Сейчас — `404 Not Found` (роута нет) → 🔴.
2. Реализация: добавить роут в точке входа проекта → 🟢.
3. Рефактор: вынести валидацию в отдельный хелпер → тесты всё ещё 🟢.

## Алгоритм для UI (компонент с поведением)

```markdown
1. ✅ Базовая проверка: команда тестов проекта.
2. 🟥 Создать тест рядом с компонентом:
   - Сценарий: «рендерит заголовок», «показывает ошибку», «открывает диалог при клике».
   - Прогнать → должен быть красным (Red).
3. 🟩 Реализовать компонент → 🟢.
4. (Опц.) Визуальная проверка через dev-сервер + browser-инструмент.
5. ✅ Финальная проверка: чек-чейн из `.agents/shared/checks.md`.
```

## Red-Green-Refactor в три итерации максимум

Если за **3 итерации** тест не стал зелёным — остановись, переключись на `interview` (возможно требование неверно понято) или `ponytail` (возможно задача решается проще). Не зацикливайся.

## Чего НЕ делать

- Не писать тест «чтобы был» — тест должен проверять **поведение**, а не существование файла.
- Не покрывать 100% слепо: покрывай ветки, которые могут упасть (валидация, граничные значения, ошибки БД).
- Не пропускать рефакторинг только потому, что «и так работает» — но и не раздувать абстракции (см. `ponytail`).

## Связанные скиллы

- **`interview`** — до теста: выяснить success-criteria и edge-cases.
- **`plan`** — многошаговые фичи: тесты пишутся шагами, не все сразу.
- **`ponytail`** — если тест «не лезет» в существующий модуль — может, нужна абстракция; проверить ponytail-ом.
- **`verify`** — финальная проверка перед коммитом.
